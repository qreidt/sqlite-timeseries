# Benchmark

Compares **ingest speed**, **storage size** and **query latency** of SQLite engines (plain tables today, this project's extension once it builds) with **TimescaleDB**, on identical data generated by the [Time Series Benchmark Suite (TSBS)](https://github.com/timescale/tsbs).

## How it works

```text
TSBS (Docker)            tsbench convert               loaded by every engine
tsbs_generate_data  -->  tags.csv  cpu.csv        -->  SQLite engines  (tsbench load / size / query / compress)
fixed seed               tags.parquet cpu.parquet      TimescaleDB     (timescaledb-parallel-copy, TSBS query runner)
                         manifest.json                          |
                                                                v
                                                  tsbench report  ->  results/<dataset>/report.md
```

1. **Generate.** TSBS writes the dataset once, from a fixed seed, so it is reproducible.
2. **Convert.** `tsbench` turns TSBS's output into plain CSV and Parquet (zstd) files plus a `manifest.json` with the schema, row counts and TSBS parameters. Field values are copied from TSBS unchanged. Times are UTC with microsecond precision, PostgreSQL's precision.
3. **Load the same CSV into every engine.** SQLite engines load through the `tsbench` harness. TimescaleDB loads through `timescaledb-parallel-copy` in Docker, into the schema TSBS's own loader creates.
4. **Query.** Both sides run the TSBS "devops" query set: TimescaleDB through TSBS's runner, SQLite through `tsbench`, with the same query shapes written for SQLite.
5. **Compress and repeat.** Engines with a compression step (TimescaleDB's columnstore, later the extension) are compressed, measured again and queried again.
6. **Report.** Every step writes a JSON file to `results/<dataset>/`. `tsbench report` combines them into `report.md`.

## Requirements

- **bash**: Linux, macOS or **WSL 2 on Windows**. Run the scripts from a WSL shell, not PowerShell.
- **Docker** with Compose v2. On Windows, use Docker Desktop with WSL integration turned on.
- **Rust** ([rustup](https://rustup.rs)) to build `tsbench`.
- **Disk space**, roughly: `small` needs under 1 GB. `main` needs about 70 GB, mostly for the databases (SQLite about 15–19 GB each, TimescaleDB about 22 GB uncompressed). These figures are estimates from test runs; check the first run.

### On Windows: keep data on the Linux filesystem

WSL reaches `C:\` (`/mnt/c/...`) through a slow file-sharing layer, which would distort both SQLite and Docker numbers. Clone the repository inside WSL (for example `~/projects`), or keep it where it is and move the data with a `config.local.env` file next to `config.env`:

```bash
DATA_ROOT=$HOME/tsbench/data
DB_ROOT=$HOME/tsbench/dbs
```

The scripts print a warning when the data or database folders are on a Windows drive.

## Quick start

```bash
cd benchmark
bash scripts/setup.sh            # once: builds the tools image, pulls TimescaleDB, builds tsbench
bash scripts/run-all.sh small    # 100 hosts x 1 day; takes a few minutes
```

The report is at `results/<dataset>/report.md`. When that works, run the size most published TSBS results use:

```bash
bash scripts/run-all.sh main
```

| Preset | Hosts | Time range | Rows | Metrics | Notes |
|---|--:|---|--:|--:|---|
| `small` | 100 | 1 day | 864K | 8.6M | Fast feedback while developing |
| `main` | 4,000 | 3 days | 103.7M | 1.04B | Same size as the TSBS README example |
| `cardinality` | 100,000 | 90 minutes | 54M | 540M | Many short series; only query types with 1-hour windows fit |

Without a preset, the values in `config.env` apply.

## Steps

`run-all.sh` runs these in order. Each one can also run alone, and each reuses what the previous ones produced.

| Script | What it does | Output |
|---|---|---|
| `scripts/setup.sh` | Builds the tools image (TSBS + `timescaledb-parallel-copy` + `psql`), pulls TimescaleDB, builds `tsbench` | `harness/target/release/tsbench` |
| `scripts/generate.sh` | Generates the TSBS data, then converts it. Skips steps whose output exists; `FORCE=1` redoes them | `data/<dataset>/` |
| `scripts/bench-sqlite.sh [engine...]` | Load, size and queries for each SQLite engine; compress, size and queries again for engines that compress | `dbs/<dataset>/`, `results/<dataset>/` |
| `scripts/bench-timescaledb.sh` | The same for TimescaleDB, in Docker | `results/<dataset>/` |
| `scripts/report.sh` | Combines the results | `results/<dataset>/report.md` |

## Configuration

Settings live in `config.env`. Override them in `config.local.env` (same format, ignored by Git), in the environment (`SCALE=1000 bash scripts/run-all.sh`), or with a preset. Precedence: environment, then preset, then `config.local.env`, then `config.env`.

The main settings:

| Setting | Default | Meaning |
|---|---|---|
| `USE_CASE` | `cpu-only` | TSBS use case: `cpu-only`, `devops` or `iot`. The query set needs `cpu-only` or `devops`; `iot` is loaded and sized only |
| `SCALE`, `TS_START`, `TS_END`, `LOG_INTERVAL`, `SEED` | 100 hosts, 1 day, 10s, 123 | Dataset shape. Together they name the dataset folder |
| `QUERIES`, `QUERY_WARMUP` | 100, 5 | Measured and warm-up queries per query type |
| `QUERY_TYPES` | empty (all that fit) | Run only these query types, e.g. `"lastpoint high-cpu-1"` |
| `SQLITE_ENGINES` | `sqlite sqlite-clustered` | Engine files in `engines/` to run |
| `EXTENSION_PATH` | empty | Loadable extension for engines that declare an `extension` key |
| `TSDB_LOAD_WORKERS` | `1` | TimescaleDB load workers. `"1 8"` loads twice and reports both |
| `TS_TUNE_MEMORY`, `TS_TUNE_NUM_CPUS` | 4GB, 4 | Resources `timescaledb-tune` sizes PostgreSQL for |
| `TIMESCALE_IMAGE` | `timescale/timescaledb:2.31.0-pg17` | Pinned TimescaleDB version |

## What is measured

**Ingest.** Rows per second and metrics per second (rows × fields, TSBS's unit) for the measurement tables, committed in batches of 10,000 rows (TSBS's default). The tags table is loaded first and timed separately. SQLite has one writer, so `TSDB_LOAD_WORKERS=1` is the like-for-like TimescaleDB number. Add more workers to see what parallel loading gives TimescaleDB. For SQLite, `parser_wait_seconds` in the result file shows whether reading the CSV, rather than SQLite, limited the rate.

**Storage.** Total bytes on disk after a checkpoint, and bytes per metric. For SQLite that is the database file plus any block-file directory; for TimescaleDB it is `hypertable_size` plus the tags table. The report includes three baselines:

- 16 bytes per metric: an uncompressed 8-byte timestamp plus an 8-byte value, the reference the Gorilla paper uses
- the CSV files
- the Parquet (zstd) files

**Queries.** The 16 query types of TSBS's devops use case. Each type runs `QUERIES` times on one connection, after `QUERY_WARMUP` unmeasured runs. The report shows the median and p95.

| Query type | What it asks |
|---|---|
| `single-groupby-M-H-T` | max of M CPU metrics per minute, for H random hosts, over a random T-hour window |
| `cpu-max-all-H` | max of all 10 CPU metrics per hour, for H hosts, over 8 hours (`-32-24`: 32 hosts, 24 hours) |
| `double-groupby-M` | average of M metrics per hour per host, for all hosts, over 12 hours |
| `groupby-orderby-limit` | max `usage_user` per minute for the last 5 minutes before a random time |
| `high-cpu-all`, `high-cpu-1` | rows with `usage_user > 90`, for all hosts or one host, over 12 hours |
| `lastpoint` | the latest row for every host |

Query types that do not fit the dataset are skipped, for example 12-hour windows on 90 minutes of data, or 32 hosts at a scale of 20. `tsbench list-queries --data-dir <dataset>` shows which apply.

On `main`, some types are slow on plain SQLite: `groupby-orderby-limit` aggregates every row before a random time, and `double-groupby-*` reads 12 hours of all 4,000 hosts. At `QUERIES=100` the query phase can take an hour or more per SQLite engine. Lower `QUERIES` or pick types with `QUERY_TYPES` for quicker runs.

**Compression.** TimescaleDB converts every chunk to the columnstore (segment by `tags_id`, order by `time DESC`), timed, then sizes and queries are measured again under the engine name `timescaledb-compressed`. SQLite engines do the same once their engine file has a `compress` step.

## Reading the results fairly

- **Same data, same durability.** Every engine loads the same CSV bytes. SQLite runs in WAL mode with `synchronous=FULL`, so each commit is durable, like PostgreSQL's default `synchronous_commit=on`.
- **Memory.** SQLite gets a 256 MiB page cache (`cache_size` in the engine files). TimescaleDB is tuned for `TS_TUNE_MEMORY`. Both also use the OS file cache. Change them together if you change one.
- **Round trips.** TimescaleDB latencies are measured over a client-server connection; SQLite runs in-process. For sub-millisecond queries, the round trip alone favours SQLite.
- **Query parameters.** All SQLite engines get identical query instances from a seeded generator. TSBS generates TimescaleDB's queries with Go's random generator, so its hosts and time windows follow the same distribution but are different draws. Compare medians, not single queries.
- **Synthetic values.** TSBS's CPU metrics are random walks over whole numbers from 0 to 100. SQLite stores whole-number REAL values as small integers, which flatters plain SQLite's size here, and real sensor data compresses differently. Use other datasets alongside this one before drawing conclusions about compression.
- **Warm cache.** Queries run right after loading, on a warm cache, on both sides.

## Adding the extension

The extension does not exist yet, so `engines/timeseries.toml` follows the API in the requirement docs (`create_hypertable`, `create_hypertable_index`, `set_compression`, `compress_chunk`, `timeseries_chunks`, `time_bucket`). When the extension builds:

1. Point `EXTENSION_PATH` at the built library, for example in `config.local.env`:
   `EXTENSION_PATH=../target/release/libtimeseries.so` (relative paths are relative to this folder).
2. Update the SQL in `engines/timeseries.toml` to match the real API. The harness needs no changes.
3. Run only the new engine against the existing data and results:
   `bash scripts/bench-sqlite.sh timeseries && bash scripts/report.sh`

Sealed block files are counted in the size, because the engine sets `block_dir = true` (requirement BF-01: `metrics.db` keeps its blocks in `metrics/`).

### Engine files

An engine is a TOML file of SQL templates, so a new schema to compare is a new file in `engines/`:

| Key | Purpose |
|---|---|
| `time_unit` | Unit of the INTEGER `time` column: `s`, `ms`, `us` or `ns` |
| `pragmas` | Run on every connection, in order |
| `create_table`, `setup` | Run once per measurement table, before loading |
| `post_load` | Run once per table after loading; not part of the ingest time |
| `compress` | Optional compression step |
| `bucket` | SQL expression for time buckets in queries |
| `extension`, `block_dir` | Load a native extension; count its block directory in the size |

Placeholders: `{table}`, `{field_columns}`, `{fields}`, `{time_unit}`, `{chunk_interval}` (an integer in `time_unit`), `{chunk_interval_text}` (`12 hours`). In `bucket`: `{time}` and `{width}`.

## Using `tsbench` directly

```bash
T=harness/target/release/tsbench
D=data/<dataset>

$T convert --input tsbs-output.gz --out-dir $D --scale 100 ...     # TSBS -> CSV + Parquet + manifest
$T load    --engine engines/sqlite.toml --data-dir $D --db /tmp/x.db --results-dir results/<dataset>
$T size    --engine engines/sqlite.toml --data-dir $D --db /tmp/x.db
$T query   --engine engines/sqlite.toml --data-dir $D --db /tmp/x.db --queries 20 --dump-sql /tmp/queries.sql
$T query   ... --types lastpoint,high-cpu-1                          # a subset of query types
$T report  --results-dir results/<dataset>
```

`--dump-sql` writes every query it runs, which helps when comparing query plans (`EXPLAIN QUERY PLAN`). `tsbench <command> --help` lists all options.

The CSV and Parquet files work with other tools too, for example DuckDB: `SELECT * FROM 'data/<dataset>/cpu.parquet'`.

## Layout

```text
benchmark/
├── config.env                  settings (override in config.local.env)
├── docker-compose.yml          TimescaleDB + the tools image
├── docker/tools/               Dockerfile (TSBS, timescaledb-parallel-copy, psql) and the TimescaleDB run script
├── engines/                    SQLite engine definitions (sqlite, sqlite-clustered, timeseries)
├── harness/                    tsbench, the Rust harness
├── scripts/                    setup, generate, bench-sqlite, bench-timescaledb, report, run-all
├── data/<dataset>/             generated: TSBS output, CSV, Parquet, manifest.json, TimescaleDB SQL, TSBS query files
├── dbs/<dataset>/              generated: SQLite databases
└── results/<dataset>/          generated: result JSON files and report.md
```

`data/`, `dbs/` and `results/` are ignored by Git.

## Troubleshooting

- **Port 5432 is in use.** Set `TSDB_PORT` to another port.
- **A `TS_TUNE_*` change has no effect.** TimescaleDB applies them only when its data volume is created. Run `docker compose -f docker-compose.yml down -v` to delete the volume and its data.
- **The tools image fails to build TSBS.** TSBS dates from Go 1.15 and is built with Go 1.17 here. Try another version: `docker compose -f docker-compose.yml build --build-arg TSBS_GO_IMAGE=golang:1.16-buster tools`.
- **`Permission denied` running a script.** Run it with `bash scripts/<name>.sh`.
- **`$'\r': command not found`.** The scripts got Windows line endings. `.gitattributes` keeps them as LF for Git; for a copied folder, run `sed -i 's/\r$//' scripts/*.sh config.env docker/tools/*.sh`.
- **Inspect the TimescaleDB database.** Set `TSDB_KEEP_RUNNING=true`, then connect with `psql -h 127.0.0.1 -U postgres -d benchmark` (password `bench`).
